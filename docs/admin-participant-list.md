# Admin participant list

Local optimization update: search waits 300 ms before querying, and the page query stays disabled while the text is still debouncing; when filters/page change, React Query's abort signal is forwarded to PostgREST so an obsolete in-flight page read can be cancelled. The first realtime subscription does not trigger a duplicate initial refresh; broadcasts and visibility refreshes remain enabled. The page query relies on that explicit visibility refresh and disables TanStack's separate window-focus refetch. Page and category-option queries do not retry automatically; explicit retry controls remain available, and a category-options failure no longer hides a successfully loaded participant list. Select All requests IDs only; list rows request specific columns. Non-college categories are read from the caller-scoped `admin_participant_categories` function after festival loading. Both functions in the local migration must be deployed before this page. Runtime parity and query performance remain unverified.

The admin participant page requests a 50-row page from `admin_filtered_participants`, using the authenticated Supabase client. The SQL function is `SECURITY INVOKER`: participant and registration SELECT privileges and row-level policies apply to the caller. Search, category, status, gender and competition conditions are evaluated before pagination; competition uses visible registrations for the active festival and the chosen item. The page and category-option cache keys include user and tenant. The shared participant list used by other screens remains unchanged.

Select All loads matching participant IDs in batches and replaces the selection with those IDs. CSV download loads every matching participant. Opening the export dialog loads no participant report data; team-based report selection reads only team option metadata. On download, item verification loads registrations for the selected item and their participants; team reports load visible participants for the selected team, registrations belonging to that team, and null-organisation direct or group registrations linked to those participants. Participant and registration ID lists are chunked; all table reads use the authenticated client and existing RLS. Group expansion and report status rules remain unchanged. PDF generation code is dynamically imported when download starts. Read failures stop export or selection rather than using a partial result.

The migration `20261029011428_admin_participant_filtered_list.sql` must be applied before this version of the page can query the functions. It adds two read-only functions, not a table or policy. Full authenticated PostgREST and responsive UI verification remains pending; catalog inspection confirmed the deployed function definitions and permissions during the release review. Multi-request exports and Select All are not transactional snapshots; concurrent edits may require a retry and same-count changes cannot always be detected. Query performance and exact-count cost require measurement with representative data and RLS.

## Pattern for future pages

This is the intended pattern for this local implementation, not a claim that it has passed production validation. Before adapting it to another page, trace its existing filters, authorization, counts, exports, selection and other consumers. Apply all list filters in the database before the page limit, use a deterministic order with a unique tie-breaker, and isolate cache keys by user, tenant, filters and page. Reset the page when filters or access scope change. Keep complete-result operations explicit and fail on incomplete reads; load report data only when the chosen report is generated. Preserve existing RLS and verify the effective deployed policies rather than trusting client-supplied scope.

Validate filter equivalence, multi-page results, null values, concurrent edits, exports, bulk actions, authorization and responsive states on representative data. Measure authenticated query plans and count cost before adding indexes. Deploy any required additive database function before its frontend consumer and verify both; do not disable shared reads used by other pages without tracing their consumers. Document the actual deployment and any unresolved limitations separately.

## Participant detail read timing

Team PDF membership discovery uses `registrations!inner` and an active-festival filter. Registration SELECT RLS therefore restricts membership IDs before they are returned, even when existing membership policies are broader. This query correction does not change any RLS policies or require another migration.

The list page fetches active festival item definitions for its competition filter at load. The participant detail route fetches that participant's details without loading the shared unpaged participant list. Its Assigned Items section starts collapsed; opening it enables the selected participant's direct and group registration reads with embedded items. Loading and retry states are shown in the section. Other consumers retain the hook's default behavior. These observations are from code inspection, not browser network measurements.
